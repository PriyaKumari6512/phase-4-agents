### tofu_validate failure: sandbox plugin crash (HCL not verified)

`tofu_validate` fails in `envs/dev/core`, `envs/stg/core` and `envs/prod/core` with the same message in each: the `hashicorp/aws` 6.73.0 provider plugin (`.terraform/providers/registry.opentofu.org/hashicorp/aws/6.73.0/linux_amd64/terraform-provider-aws`) could not start in the check sandbox ("Unrecognized remote plugin message: Failed to read any lines from plugin's stdout", i.e. the go-plugin handshake failed). OpenTofu therefore could not load the provider schema, and it stops at the first resource it needs the schema for.

Evidence that the cause is the environment and not the HCL:
- The error text contains no HCL diagnostic such as an unknown argument, an unsupported attribute or a missing variable.
- The resource named in each error differs per environment (`aws_s3_bucket_cors_configuration` in dev, `aws_vpc_block_public_access_exclusion` in stg, `aws_vpc_security_group_ingress_rule` in prod). The failing resource is only where the schema read happened to fail; it is not a finding about that resource.
- The plugin file is present, is executable (`-rwxr-xr-x`) and is owned by the sandbox user, so this is not a missing file or a permissions problem. The message lists other possible causes (wrong architecture, missing libraries); these were not investigated, and the sandbox, not the repo, is where they would be fixed.
- `tofu_fmt`, `tflint`, `trivy`, `checkov`, `actionlint`, `helm_lint`, `kubeconform`, `gitleaks` and `conftest` all pass on the same files.
- Per request 4, `infra_validate` was not run again and no `.tf` or YAML file was changed in this round. The check result above is the one recorded by the last validation run. Only this PR.md was edited.

## Notes from the architecture

- ADR-0005 / architecture section 3 says 'no Kubernetes' and names a managed container service plus static hosting for ctr-web; the golden-path catalog only renders AWS + Kubernetes (EKS/Argo CD/Helm), so deploy_target=kubernetes is the closest catalog expression and needs platform-team sign-off (section 8 deployment table differs).
- Region ap-south-1 (Mumbai) chosen for the India hosting constraint CON-008; hosting is still open (Q-008, RSK-008).
- ctr-web is a static React SPA on CDN: the catalog has no CDN/static-site template (needs object_storage + cdn recorded); CDN, WAF and /api routing at the edge are not expressible.
- The architecture states no monthly budget.
- Data classification: the API and DB hold PII (names, phones, birth years) but no clinical, payment or insurance data (CON-006), so they are recorded as confidential, not restricted; the org rule forbids a public endpoint on restricted services, and the API is the public entry point behind the edge.
- Prod: 2 API replicas across two zones, scale 2-4 on CPU>60%; managed PostgreSQL 16 with btree_gist, synchronous HA standby, RPO 15 min / RTO 1 h, backups kept 14 days (verify the RDS template covers multi-AZ in prod, PITR, 14-day retention and the btree_gist extension). Dev and stg: single-node DB, 1 replica.
- Reminder dispatcher and scheduled jobs run inside the API process; there is no separate worker.
- Provider webhooks (rel-009, rel-010) need a public path on the API; HMAC verification is in the app; WAF rate limits are not expressible in the catalog.
- Secrets are references only: DB credentials, provider API keys, webhook HMAC secrets, JWT signing key. Staging uses provider sandbox accounts.
