## Notes from the architecture

- Cloud is AWS only, region ap-south-1 (Mumbai), per ASM-009; ap-south-1 is in the catalog allowed regions.
- Deploy target is ecs_fargate per architecture section 8: ECS Fargate service gym-api behind an Application Load Balancer with WAF; ctr-web is static files on S3 and CloudFront.
- NFRs (design objectives, no SLA): check-in lookup p95 server <= 500 ms and screen <= 2 s; member pages p95 <= 3 s on 4G; availability 99.5% monthly during gym hours 06:00-22:00 India time; 99% of captured payments reflected within 2 minutes; >= 95% of due reminders sent on due day; RPO <= 15 minutes, RTO <= 1 hour; ctr-web RTO <= 30 minutes.
- Capacity: about 1 request per second at peak with 3x headroom; 2 API tasks of 0.5 vCPU and 1 GB across 2 zones for availability, scaling to 4 when CPU is above 60% for 5 minutes; prod database Multi-AZ 2 vCPU 8 GB 50 GB with growth; stg and dev use 1 task, single-zone database, smaller tier.
- Constraints: no native app, client's existing Razorpay account, WhatsApp only (never SMS), English only, no card or UPI data stored or logged, DPDP practice with no health data, launch 1 January 2027 (assumed).
- Data classification: PII (names, phones) and payment records are treated as confidential; no card or UPI details are held. Encryption at rest for database, backups and S3; TLS on all edges.
- Secrets are held in AWS Secrets Manager and passed to the task as environment variables; only names are listed here, never values.
- Architecture names a Secrets Manager and WAF; ALB with WAF, network (VPC), ECS cluster and registry are platform needs derived from the ECS Fargate target.
- Catalog has no WAF template and no secrets template for ECS; any gap should be reported by validation rather than substituting another topology.
- Repository identities supplied: acme/gym-api (backend ctr-gym-api) and acme/gym-web (ctr-web).
- Jobs and outbox run inside the API and use the database, so no queue or cache component is needed (ADR-0005, no cache per ADR-0002).
- Approval is owned by the DevOps Lead and Solution Architect; code renders templates, validates output and makes bounded repairs of flagged files.
